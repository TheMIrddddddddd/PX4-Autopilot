# 017 ST-Link 烧录 bootloader 和主程序成功

时间：2026-06-27 18:27:55

## 概念
本次确认当前 H743 最小系统板的日常优先烧录方式改为：

```text
ST-Link / SWD + STM32CubeProgrammer CLI
```

原因是 ST-Link 已经实测可以完成两个关键地址的写入和校验：

- PX4 bootloader：`0x08000000`
- PX4 default 主程序：`0x08020000`

## 代码/流程
本次没有修改 PX4 源码，只验证并更新文档中的烧录流程。

bootloader 烧录命令：

```bash
STM32_Programmer_CLI -c port=SWD mode=UR reset=HWrst freq=1000 \
  -w build/gjl_h743mini_bootloader/gjl_h743mini_bootloader.bin 0x08000000 \
  -v
```

主程序烧录命令：

```bash
STM32_Programmer_CLI -c port=SWD mode=UR reset=HWrst freq=1000 \
  -w build/gjl_h743mini_default/gjl_h743mini_default.bin 0x08020000 \
  -v -rst
```

主 MD 已更新：

- 当前优先烧录方式改为 `ST-Link / SWD + STM32CubeProgrammer CLI`。
- 第 8 节中，`ST-Link / SWD` 改为 `8.1 当前优先使用`。
- `STM32 ROM DFU` 改为 `8.2 备选方式`。

## 常见坑
- 如果主程序烧录过程中断，`0x08020000` 后面的主程序区域可能不完整，需要重新完整烧录主程序。
- `Unable to get core ID` 表示 ST-Link 没有成功连接到目标内核，优先使用 `mode=UR reset=HWrst freq=1000` 重试。
- `DEV_USB_COMM_ERR` 更偏向 ST-Link 自身 USB 通讯异常，优先拔插 ST-Link，或在 Linux 下软复位 ST-Link USB 设备。
- `No STM32 device in DFU mode connected` 不代表 ST-Link 不能烧录；DFU 和 ST-Link 是两条不同烧录链路。

## 调试方法
确认 ST-Link：

```bash
STM32_Programmer_CLI -l
```

确认烧录成功的关键输出：

```text
Download verified successfully
MCU Reset
Software reset is performed
```

确认 PX4 主程序启动后的 USB 枚举：

```bash
lsusb | grep -Ei "3185|0483"
```

期望能看到：

```text
3185:0038 Auterion PX4 FMU v6C.x
```

## 复盘要点
当前阶段优先使用 ST-Link 是为了让烧录路径更可控。STM32 ROM DFU 仍然保留为备选方式，但不再作为当前日常优先方式；PX4 bootloader upload 继续作为后期目标，等 board id、`.px4` 包和上传握手都稳定后再推进。

验收标准：

- 烧录后能进 NSH。
- `dmesg` 中不再集中出现大量当前未接外设的启动失败日志。
