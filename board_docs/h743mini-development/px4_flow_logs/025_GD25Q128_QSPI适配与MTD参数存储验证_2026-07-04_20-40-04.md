## 概念

### GD25Q128 与 W25QXXXJV 驱动的关系

GD25Q128 是 SPI NOR Flash，当前这颗芯片通过 QSPI 引脚连接到 STM32H743。

本轮使用的是 NuttX 中已有的 `w25qxxxjv.c` 驱动。虽然驱动名字是 W25Q 系列，但 SPI NOR Flash 的 JEDEC ID、读状态寄存器、写使能、页编程、扇区擦除等命令是高度兼容的。

本板实测 JEDEC ID：

```text
c8 40 18
```

含义：

- `0xc8`：GigaDevice 厂商 ID。
- `0x40`：memory type。
- `0x18`：容量编码，对应 `128 Mbit = 16 MiB`。

如果是 W25Q64，容量编码通常会是 `0x17`；本轮识别到的 `0x18` 对应的是 GD25Q128 级别容量。

### QSPI 硬件读通不等于 MTD 可用

GD25Q128 可用至少要经过几层：

```text
原理图引脚正确
 -> GPIO/QSPI 基础收发正确
 -> STM32H7 QSPI 外设命令流程正确
 -> w25qxxxjv 能读 JEDEC 并建立几何信息
 -> PX4 MTD 能 attach QSPI 设备
 -> board manifest 能创建分区
 -> param/mtd 工具能读写验证
```

本轮问题不是单点故障，而是这些层级逐步打通的过程。

### MTD 分区单位

GD25Q128 当前 MTD 几何：

```text
blocksize:    256
erasesize:    4096
neraseblocks: 4096
```

解释：

- `blocksize = 256`：逻辑读写块，对应 Flash page 大小。
- `erasesize = 4096`：最小擦除扇区。
- `neraseblocks = 4096`：整颗芯片共有 4096 个 4 KiB 扇区。

整颗芯片容量：

```text
4096 * 4096 = 16777216 bytes = 16 MiB
```

当前分区：

```text
/fs/mtd_params     512 * 256 = 131072 bytes = 128 KiB
/fs/mtd_waypoints  512 * 256 = 131072 bytes = 128 KiB
```

`mtd status` 中 partition 显示的 `blocks: 32` 是按 4 KiB erase block 算：

```text
32 * 4096 = 131072 bytes
```

因此当前 GD25Q128 只主动分配了 256 KiB，剩余空间暂未使用。

### dataman 与 /fs/mtd_waypoints 的关系

当前保持 PX4 官方默认：

```text
dataman -> /fs/microsd/dataman
```

`/fs/mtd_waypoints` 只是已经创建好的 MTD 分区，不等于 dataman 已经迁移过去。

当前决定：

- 参数：使用 `/fs/mtd_params`。
- dataman：继续使用 `/fs/microsd/dataman`。
- `/fs/mtd_waypoints`：保留为已验证备用分区。

## 排查过程

### 阶段 1：先判断硬件是否真的通

最初不能直接假设 NuttX QSPI 驱动正确，也不能直接判断芯片损坏。

排查思路：

1. 如果 GPIO bitbang 都读不到 JEDEC，优先查硬件：电源、CS、CLK、IO0/IO1、WP/HOLD、引脚复用。
2. 如果 GPIO bitbang 能读到 JEDEC，但硬件 QSPI 卡死，优先查 QSPI 外设配置或驱动流程。
3. 如果硬件 QSPI 能读 JEDEC，但 MTD 失败，再查 W25Q 驱动和 PX4 MTD attach。

本轮 GPIO bitbang 读到：

```text
c8 40 18
```

因此第一步把问题从“硬件完全不通”缩小到“QSPI 外设或上层驱动路径”。

### 阶段 2：修复 STM32H7 QSPI 外设驱动等待问题

原 `stm32_qspi.c` 中 `qspi_waitstatusflags()` 是无超时死等：

```c
while (!(SR & mask))
  ;
```

如果状态位永远不变，系统就会卡死。

修复方向：

- 增加 `QSPI_WAIT_TIMEOUT`。
- 把 `qspi_waitstatusflags()` 从 `void` 改为 `int`。
- 超时后返回 `-ETIMEDOUT`，并打印 mask、polarity、SR。
- 在关键读写路径检查返回值。

意义：

- 调试时不会再因为一个状态位错误导致整个 NSH 卡死。
- 后续能从日志看到到底在等哪个 QSPI 状态位。

### 阶段 3：修复 polling 模式下读命令 FMODE 错误

硬件 QSPI JEDEC 读取使用的是 `0x9f`，这是读命令。

原 polling 模式中，`qspi_command()` 先统一按 indirect write 配置：

```c
CCR_FMODE_INDWR
```

但 JEDEC ID 读取应该使用：

```c
CCR_FMODE_INDRD
```

修复后按读写方向分别配置：

```c
if (QSPICMD_ISWRITE(cmdinfo->flags)) {
	qspi_ccrconfig(priv, &xctn, CCR_FMODE_INDWR);
} else {
	qspi_ccrconfig(priv, &xctn, CCR_FMODE_INDRD);
}
```

这一步是 `mtd qspi_jedec_hw` 从卡死变成能读出 `c8 40 18` 的关键。

### 阶段 4：避免重复等待已清除的 TCF

原逻辑中，部分收发函数内部已经等待并清除了 `TCF`，外层又再次等待：

```c
qspi_waitstatusflags(priv, QSPI_SR_TCF, 1);
qspi_waitstatusflags(priv, QSPI_SR_BUSY, 0);
```

如果内部已经清掉 `TCF`，外层再等它变成 1，就可能再次卡住。

修复方向：

- 让收发函数内部负责完成等待和清标志。
- 外层避免重复等待已被清除的 `TCF`。

### 阶段 5：让 PX4 MTD 能识别 QSPI 设备

QSPI 外设能读 JEDEC 后，仍然不能自动变成 PX4 参数存储。

还需要：

1. `px4_manifest.h` 增加 `QSPI` bus type。
2. `px4_mtd.cpp` 增加 QSPI attach。
3. `boards/gjl/h743mini/src/mtd.cpp` 增加 `qspi_flash` 和 `gd25q128` entry。

这一步把“硬件驱动能读 ID”推进到“PX4 MTD 能创建 `/fs/mtd_params`”。

### 阶段 6：处理写擦压力测试饿 USB/MAVLink

`mtd -i 1 rwtest` 后 QGC 断开，但最终 `rwtest OK`。

这个现象容易误判成：

- QSPI 不稳定。
- USB 掉线。
- 需要开 DMA。
- GD25Q128 写失败。

实际分析：

- `rwtest OK` 说明写擦验证成功。
- QGC 断开是通信任务被饿住，不是数据错误。
- 写 Flash 时真正慢的是 Flash 内部 program / erase busy，不是 MCU 搬运数据。

在 `w25qxxxjv.c` 中，原等待是紧循环：

```c
while ((w25qxxxjv_read_status(priv) & STATUS_BUSY_MASK) != 0);
```

以及 WEL 等待：

```c
while ((status & STATUS_WEL_MASK) != STATUS_WEL_ENABLED);
while ((status & STATUS_WEL_MASK) != STATUS_WEL_DISABLED);
```

修复为在未满足条件时让出 CPU：

```c
nxsig_usleep(1000);
```

结果：

- `rwtest` 仍需等待 Flash 写擦完成。
- QGC 不再断开。
- MAVLink heartbeat 正常。

### 阶段 7：清理临时调试命令

bring-up 过程中临时加入过：

```text
mtd qspi_jedec
mtd qspi_jedec_hw
```

用途：

- `qspi_jedec`：GPIO bitbang 验证硬件基础链路。
- `qspi_jedec_hw`：验证 STM32H7 QSPI 外设命令路径。

确认 QSPI / MTD / param 全链路通过后，本轮已删除这两个临时命令，避免长期污染 `mtd` 系统命令。

- 修复 `w25qxxxjv.c` 编译格式警告。
- 在 `w25qxxxjv.c` 的 Flash busy / WEL 等待中加入 `nxsig_usleep(1000)`，避免饿死 USB/MAVLink。
- 验证参数保存和重启持久化。
- 删除临时 QSPI JEDEC 调试命令和空调试文件。

### 暂不处理

- 暂不启用 QSPI DMA。
- 暂不把 dataman 从 `/fs/microsd/dataman` 迁移到 `/fs/mtd_waypoints`。
- 暂不使用 GD25Q128 剩余全部空间，只先分配 `/fs/mtd_params` 和 `/fs/mtd_waypoints` 各 128 KiB。

暂不启用 DMA 的原因：

- 当前 QGC 断开问题已经由 busy wait 让出 CPU 解决。
- DMA 只能减少 QSPI 数据搬运时的 CPU 占用，不能缩短 Flash 内部 erase / program 时间。
- STM32H7 上启用 DMA 还要额外面对 DCache、buffer 对齐和 DMA 可访问内存问题。
- 当前参数存储和 MTD 压力测试已经满足阶段目标。

- `/fs/mtd_waypoints` 已创建，但当前不接入 dataman。
- dataman 保持 PX4 官方默认 `/fs/microsd/dataman`。
- `/fs/mtd_caldata` 当前没有工厂校准数据，`param dump /fs/mtd_caldata` 显示 BSON no data 是正常状态。
- `mtd -i 1 rwtest` 不再导致 QGC 断开，说明 Flash 写擦等待期间 USB/MAVLink 调度已恢复。

## 常见坑

### 1. 读到 JEDEC 不等于 MTD 已经可用

JEDEC 只证明芯片 ID 能读出来。真正用于 PX4 参数存储，还需要：

- QSPI 外设稳定。
- NOR Flash 驱动识别容量。
- MTD 分区创建成功。
- 参数系统选择 `/fs/mtd_params`。
- `param save` 和重启后导入正常。

### 2. QSPI 卡死不能只怀疑硬件

本轮 GPIO bitbang 读 JEDEC 成功，硬件 QSPI 卡死。这个组合说明：

- 基础硬件链路很可能是通的。
- 更应该看 QSPI 外设 FMODE、状态位等待和驱动流程。

### 3. QGC 断开不一定是飞控重启

如果 `rwtest` 最后能继续打印 `rwtest OK`，说明测试进程还在执行。

这种情况更像：

- CPU 长时间忙等。
- MAVLink / USB 任务调度不及时。
- QGC heartbeat 超时后显示断开。

### 4. DMA 不是所有卡顿的解药

Flash 写擦包含两段：

```text
数据传输阶段：DMA 可能有帮助
芯片内部擦写 busy 阶段：DMA 没法加速
```

本轮问题主要在第二段 busy wait，因此先加 sleep/yield 比直接开 DMA 更合理。

### 5. /fs/mtd_waypoints 不等于 dataman

当前 PX4 官方默认 dataman 路径是：

```text
/fs/microsd/dataman
```

`/fs/mtd_waypoints` 是一个 MTD 分区，只有修改 dataman 启动命令为 `dataman start -f /fs/mtd_waypoints` 后才会被 dataman 使用。本轮选择不迁移。

### 6. /fs/mtd_caldata 为空不代表 EEPROM 坏

`/fs/mtd_caldata` 存的是工厂校准导出的 `CAL_`、`TC_` 参数。

如果没有启用：

```text
SYS_FAC_CAL_MODE=1
```

并执行工厂校准，里面为空是正常的。

## 调试方法

本轮形成的调试顺序：

1. 看原理图，确认 GD25Q128 是 QSPI 还是普通 SPI。
2. 在 NuttX pinmap 里确认每个 QSPI 引脚宏是否存在。
3. 打开 `CONFIG_STM32H7_QUADSPI` 和 `CONFIG_MTD_W25QXXXJV`。
4. 用最小 JEDEC ID 读取验证硬件链路。
5. 如果硬件 QSPI 卡死，先给等待函数加 timeout。
6. 检查 QSPI command 的读写模式，尤其是 `CCR_FMODE_INDRD` / `CCR_FMODE_INDWR`。
7. 确认 `w25qxxxjv_initialize()` 能识别容量。
8. 接入 PX4 MTD manifest，创建 `/fs/mtd_params`。
9. 用 `mtd status` 看几何和分区。
10. 用 `mtd readtest` / `mtd rwtest` 验证读写。
11. 用 `param save` / `reboot` 验证参数持久化。
12. 如果压力测试导致 QGC 断开，区分“系统复位”还是“通信任务被饿住”。

## 复盘要点

这次问题的核心价值在于：不是把一个配置项打开就结束，而是把嵌入式存储 bring-up 按层拆开。

可以总结成四个判断：

1. 先证明硬件基础链路：JEDEC ID 是最小闭环。
2. 再证明外设驱动流程：QSPI read command 不能走 write mode。
3. 再证明系统集成：PX4 MTD 需要 manifest 和 attach 路径。
4. 最后证明运行时稳定性：写擦时不能饿死 USB/MAVLink。

这也是面试时可以重点讲的能力：

- 不把所有问题都归因于硬件。
- 不在没有证据时直接上 DMA。
- 用最小测试命令把问题分层。
- 每修一层都用可观测输出验证。
- 最后清理临时调试代码，保留可维护状态。

## 面试讲述版本

可以按这个逻辑讲：

> 我在给 STM32H743 最小系统板适配 GD25Q128 QSPI Flash 时，最开始硬件 QSPI 读 JEDEC 会卡死。为了判断是硬件问题还是驱动问题，我先写了一个临时 GPIO bitbang JEDEC 测试。这个测试能读到 `c8 40 18`，说明芯片、电源、CS、CLK、IO0/IO1 至少是通的，问题不应该优先归因于硬件。
>
> 接着我回到 STM32H7 QSPI 驱动，发现等待状态位的函数是死循环，没有 timeout。于是我先给等待函数加了超时返回，避免系统卡死。然后继续看 QSPI command 的 polling 流程，发现原逻辑对读命令也先按 indirect write 配置 FMODE，而 JEDEC ID 是读命令，应该走 indirect read。修复后，硬件 QSPI 就能读出 `c8 40 18`。
>
> 读 ID 成功以后，我没有直接认为任务完成，而是继续接 PX4 的 MTD 框架。PX4 manifest 原来没有 QSPI bus type，所以我增加了 QSPI 类型，并在 `px4_mtd.cpp` 里接入 `stm32h7_qspi_initialize()` 和 `w25qxxxjv_initialize()`，最后在板级 `mtd.cpp` 中分出 `/fs/mtd_params` 和 `/fs/mtd_waypoints`。
>
> 后续 `mtd readtest` 可以过，但 `rwtest` 时 QGC 会短暂断开。这个现象容易误判成 QSPI 不稳定或者需要 DMA，但因为最后能打印 `rwtest OK`，说明 MCU 没复位、Flash 写擦也成功了。真正的问题是 `w25qxxxjv.c` 在等待 Flash busy 清零时用紧循环，占着 CPU 导致 USB/MAVLink 任务被饿住。我在 busy wait 里加了 `nxsig_usleep(1000)`，让调度器有机会运行通信任务，之后 `rwtest` 不再让 QGC 断开。
>
> 最后我用 `param save` 和重启验证参数确实保存到 `/fs/mtd_params`，同时保持 dataman 官方默认使用 `/fs/microsd/dataman`。调试命令验证完成后也清理掉，避免把临时代码留在系统命令里。
