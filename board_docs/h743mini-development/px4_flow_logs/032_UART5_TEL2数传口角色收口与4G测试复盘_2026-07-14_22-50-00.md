## 当前测试现象

公网 4G / 云 relay 阶段性测试中观察到：

- 服务器 UDP `14560` / `mavlink-relay` 链路曾经可以收到 PX4 MAVLink。
- QGC 曾通过公网 relay 识别过链路。
- 但实际体验中 QGC 刷新慢、连接体验不如本地串口。
- 测试窗口内 PX4 侧 `sensor_accel` / `sensor_gyro` 曾出现无数据情况。
- `vehicle_attitude` 没有数据。
- `vehicle_local_position` / `vehicle_global_position` 没有数据。
- 因此 QGC 大约一秒左右刷新一次，**不能完全归因于 4G 网络慢**。
- `mavlink status` 中 tx 曾经约 `131.6 B/s`，说明 PX4 当前实际发出的有效数据也很少。
- 服务器侧稳态曾约 `~150 B/s` 量级系统流；USB 本地测速可达约 `~6 KB/s` 且可见高频 `SCALED_IMU` / `HIGHRES_IMU`。
- 用户主观判断 4G 当前不适合继续作为主调试链路，决定先放弃 4G 推进。

## 关键结论

- `UART5 PB13/PB12` 这组引脚和 TEL2/MAVLink 配置 **保留**。
- 当前口 **不再定义为「4G 专用口」**。
- 当前口以后定义为 **「TEL2 / MAVLink 数传预留口」**。
- 4G 相关服务器、relay、防火墙、DTU 配置作为阶段性测试经验记录，**不作为当前必需链路**。
- 后续如果使用普通数传电台，**不需要重新抢占 UART**；继续使用 `PB13/PB12` 即可。
- 后续如果再次启用 4G，只需要重新验证 DTU 参数、服务器 relay、腾讯云 UDP `14560`、防火墙和 QGC UDP 配置。
- 已验证该口与 TF 卡、JY901B、GPS、CRSF、电池 ADC 等规划不冲突。

## 角色收口后的 UART5/TEL2 定义

| 项 | 定义 |
|---|---|
| 硬件 | `UART5`：`PB13` = TX / `P1-33`，`PB12` = RX / `P1-32` |
| 角色 | TEL2 / MAVLink 数传预留口 |
| 优先用途 | 普通数传电台、USB-TTL MAVLink 调试、其他 MAVLink 串口设备 |
| 非用途 | 不再写为 4G 专用口 |
| 设备节点（预期） | `/dev/ttyS4`（以实测 `rc.serial_port` 为准） |
| 波特率 | 当前按 `115200`（`SER_TEL2_BAUD`） |
| MAVLink | Normal 模式；硬件流控关闭；两线不接 RTS/CTS |
| 速率 | `MAV_1_RATE` 当前约 `5000` B/s；数传稳定后可再评估提高 |

## 4G 测试复盘

### 做过什么

- 将 4G DTU 以 UDP Client 指向腾讯云 `UDP 14560`。
- 服务器部署/运行 `mavlink-relay`，学习 vehicle/GCS 端点并转发。
- QGC 通过公网 UDP 接入，曾完成链路识别与双向字节转发。

### 为什么观感差（客观）

- 4G 公网链路需要经过 DTU、运营商 NAT、腾讯云 relay、QGC，链路更长。
- DTU 可能存在串口打包间隔、弱信号、供电和 NAT 重绑定等问题。
- 对早期板级调试来说，本地串口或普通数传链路更直接、更可控。
- 当前最关键瓶颈仍是 IMU / 姿态数据源没有稳定恢复到“可供 QGC 高频使用”的状态，不适合继续把时间消耗在 4G 体验优化上。

### 保留什么

- 引脚与 TEL2 参数路径保留。
- 云 relay / 防火墙 / DTU 配置作为可复用经验，需要时再启。

## 后续使用普通数传的接线方式

| 数传模块 | H743mini | 说明 |
|---|---|---|
| RXD | PB13 / UART5_TX / TEL2_TX | 飞控发送到数传 |
| TXD | PB12 / UART5_RX / TEL2_RX | 数传发送到飞控 |
| GND | GND | 必须共地 |
| VIN | 按数传模块手册供电 | 不从 GPIO 供电，注意电压和电流 |

补充：

- 电平需与 STM32H743 的 3.3V TTL 兼容（或经电平转换）。
- 若数传默认 57600，可两边统一为 57600 或 115200。
- 地面端 USB 接电脑，QGC 选对应 COM；近程主链路不再依赖云 `14560`。

## 当前不继续推进 4G 的原因

1. 公网路径跳数多、时延与抖动大，体感明显弱于 USB/本地串口。
2. DTU/NAT/弱网变量多，早期调试成本高、可控性差。
3. 板级主矛盾是传感器/姿态数据与外设接入，不是公网链路打磨。
4. 同一 UART 留给普通数传，投入产出比更高。
